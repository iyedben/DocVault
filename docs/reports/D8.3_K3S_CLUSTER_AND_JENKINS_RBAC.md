## 1. Executive Summary

Phase D8.3 establishes the secure identity, scoped authorization, and admission-control boundaries for the Jenkins Continuous Delivery (CD) controller interacting with K3s on `docvault-srv`. Following the read-only security review and final pre-application review dated 13 November 2026, all identified findings (**F-01 through F-10 plus Service restrictions and preflight safety**) have been fully addressed across the RBAC manifests, admission policy specifications, and automated verification suites.

### Core Security Principles & Boundaries
1. **Explicit Trust Boundary (F-01):** Admission guardrails are bound strictly to requests authenticated as `system:serviceaccount:docvault:jenkins-deployer` via `matchConditions` referencing `request.userInfo.username`. The deployer's requests are strictly constrained, while administrator-managed workloads remain unhindered. This is an explicit trust boundary for deployment automation, not complete cluster-wide workload protection. Deployment security does not rely on application labels, which a deployer might manipulate.
2. **ServiceAccount Token & Credential Hardening (F-02, F-05, F-06):** Pod templates must explicitly specify `automountServiceAccountToken: false` (omitted is strictly rejected), select exclusively the approved ServiceAccount `docvault-app` (the `default` ServiceAccount is rejected), and contain zero projected `serviceAccountToken` volumes. The admission policy cannot inspect live ServiceAccount objects; an administrator must provision `docvault-app` with `automountServiceAccountToken: false`, and Jenkins is denied all permissions to create or modify ServiceAccounts. This mitigates token harvesting, though defense-in-depth requires network controls.
3. **Container Security & Workload Constraints (F-03, F-04, F-07, F-10):** Workload Pod templates (covering both `Deployments` and `Jobs`) must enforce:
   - `privileged: false` and `allowPrivilegeEscalation: false` across all containers and initContainers.
   - `runAsNonRoot: true` at Pod level, with container-level override to `false` strictly prohibited.
   - `capabilities.drop: ["ALL"]` with zero added capabilities.
   - Complete prohibition of host namespaces (`hostNetwork`, `hostPID`, `hostIPC`), `hostPath` volumes, and host ports.
   - Complete prohibition of direct Secret volume mounts, projected Secret sources, and Secret-backed environment variables (`secretKeyRef` or `envFrom.secretRef`).
   - Complete prohibition of `initContainers`, container `command` / `args` overrides, and `imagePullSecrets`.
   - Strict image provenance: images must originate from `iyedbnaissa/docvault-api` pinned by an immutable 64-character SHA-256 digest (`@sha256:[a-f0-9]{64}`). Mutable tags alone are rejected.
4. **Service Admission Restrictions (Pre-Application Remediation 1):** ValidatingAdmissionPolicy extends to core `v1.Service` objects created or updated by `jenkins-deployer`:
   - `spec.type` must be `ClusterIP` (NodePort, LoadBalancer, and ExternalName are strictly prohibited).
   - `externalIPs` are strictly prohibited.
   - Explicit `nodePort` values on Service ports are prohibited.
   - `externalName` is strictly prohibited.
   - LoadBalancer configurations (`loadBalancerIP`, `loadBalancerSourceRanges`, `loadBalancerClass`) are strictly prohibited.
   - Existing Deployment and Job guardrails (Rules 1-13) and Service guardrails (Rules 14-18) use safe CEL resource discrimination (`request.resource.resource`), ensuring no field resolution errors across object types.
5. **Safer Preflight & Application Sequencing (Pre-Application Remediation 2):** `verify_d8_3.sh` introduces a strict multi-stage lifecycle:
   - **Preflight Phase (Read-Only):** Checks `kubectl` availability, API server connectivity, existence of namespace `docvault`, API support for `ValidatingAdmissionPolicy` and `ValidatingAdmissionPolicyBinding`, and executes server-side dry-run validation of both manifests. If any preflight validation fails, the script aborts immediately (exit code 2) without applying either manifest.
   - **Safe Application Phase:** Applies RBAC manifest first, then Admission Policy manifest. If RBAC succeeds but Admission Policy fails, it reports a critical partial application state with rollback instructions and exits (exit code 3).
   - **Existence Verification:** Confirms all 5 expected resources exist on the cluster before initiating test workloads.
6. **Network Security & Egress Assessment:** Read-only inspection of K3s confirms Flannel VXLAN CNI and an active embedded NetworkPolicy controller (`kube-router` npc_iptables v2.11.1-k3s1). Admission policies do not provide network egress isolation; pods in namespace `docvault` currently possess unrestricted network egress. Future Phase D8.4/D8.5 will implement a dedicated egress NetworkPolicy.
7. **Execution Boundary Disclosure:** In compliance with the strict execution boundary, all manifests remain **unapplied to the live cluster** and `verify_d8_3.sh` has not been executed against the live cluster. Application and live verification await authorized administrative execution via MobaXterm.

### 3.2 Read-Only Network Security Assessment
A read-only audit of the running K3s system logs and process table confirmed the network configuration:
1. **CNI Architecture:** K3s runs Flannel with `vxlan` backend (`Interface flannel.1 mac address set`).
2. **NetworkPolicy Controller Enforcement:**
   - K3s embeds a dedicated NetworkPolicy controller based on `kube-router` (`npc_iptables`):
     ```
     level=info msg="Starting network policy controller version v2.11.1-k3s1"
     I1113 23:09:59.091012 1184 npc_iptables.go:43] Starting network policy controller
     I1113 23:09:59.805908 1184 npc_iptables.go:63] Starting network policy controller full sync goroutine
     ```
   - Standard Kubernetes `networking.k8s.io/v1` `NetworkPolicy` objects **are actively supported and enforced** by K3s via kernel iptables.
3. **Current Limitations & Egress Risk:**
   - **The ValidatingAdmissionPolicy does NOT provide network or egress isolation.**
   - It cannot prevent a running container from attempting network egress to the Kubernetes API server (`https://172.23.0.1:6443` or `https://10.43.0.1:443`), the kubelet (`10250`), other cluster namespaces, or external networks.
   - At present, no `NetworkPolicy` is deployed in namespace `docvault`. Workloads in `docvault` currently have unrestricted default-allow network egress.
4. **Future Egress NetworkPolicy Design (Roadmap Phase D8.4/D8.5):**
   - Merely defining a NetworkPolicy manifest provides protection only when the active CNI enforces it. Because K3s `npc_iptables` is confirmed active, an egress policy will be enforced once applied.
   - Planned egress policy:
     * **Egress DNS:** UDP/TCP port 53 to `kube-system/coredns`.
     * **Egress Database:** TCP port 5432 to `docvault-postgres` service.
     * **Default Egress Deny:** Blocks all egress to cluster API (`6443`, `443`), Kubelet (`10250`), host loopback/metadata services, and the Internet.
   - In accordance with the execution boundary, **no NetworkPolicy is applied in this remediation pass**.

## 4. Phase B & C: Remediated Scoped RBAC Architecture

Located in `k8s/rbac/jenkins-deployer-rbac.yaml`:

### 4.1 ServiceAccount (`jenkins-deployer`)
```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: jenkins-deployer
  namespace: docvault
  labels:
    app.kubernetes.io/name: docvault
    app.kubernetes.io/component: cd-deployer
    app.kubernetes.io/managed-by: manual
automountServiceAccountToken: false
```
- Bound exclusively to namespace `docvault`.
- `automountServiceAccountToken: false` guarantees that pods running as this identity do not mount default API credentials.

### 4.2 Application ServiceAccount Trust Boundary (`docvault-app`)
- The admission policy requires workload Pods to declare `serviceAccountName: docvault-app` and `automountServiceAccountToken: false`.
- **Limitation:** The admission policy evaluates workload Pod specs; it cannot inspect live ServiceAccount objects directly in the cluster state.
- **Trust Boundary Requirement:** An administrator must provision the `docvault-app` ServiceAccount in namespace `docvault` with `automountServiceAccountToken: false`.
- **RBAC Exclusion:** The `jenkins-deployer` Role strictly excludes `serviceaccounts` permissions (`get`, `create`, `update`, `patch`, `delete`). Jenkins cannot create, alter, or re-enable token projection on ServiceAccounts.
- **Disclaimer:** This boundary alone does not eliminate every theoretical credential-exfiltration vector. It ensures that Jenkins cannot use default or escalated tokens.

### 4.3 Refined Role (`docvault-deployer-role`)
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: docvault-deployer-role
  namespace: docvault
  labels:
    app.kubernetes.io/name: docvault
    app.kubernetes.io/component: cd-deployer
rules:
  # 1. Manage FastAPI application deployment rollouts
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]

  # 2. Manage database migration jobs (without unnecessary delete permissions)
  - apiGroups: ["batch"]
    resources: ["jobs"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]

  # 3. Core networking and ConfigMap release state management (HELM_DRIVER=configmap)
  - apiGroups: [""]
    resources: ["services", "configmaps"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]

  # 4. Storage claim management (without delete permission to protect persistent data)
  - apiGroups: [""]
    resources: ["persistentvolumeclaims"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]

  # 5. Read-only inspection of pods and logs for deployment health verification
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
```

### 4.4 Explicit Least-Privilege Exclusions (Negative RBAC Boundaries)
- **Zero Secret Access:** `get`, `list`, `watch`, `create`, `update`, `delete` on `secrets` are **completely omitted**.
- **No PVC Deletion:** `delete` on `persistentvolumeclaims` is omitted to protect persistent document storage from deletion.
- **No Job Deletion:** `delete` on `jobs` is omitted to preserve database migration execution records and audit trails.
- **No ServiceAccount Management:** Cannot create, inspect, or modify ServiceAccounts.
- **No RBAC Privilege Escalation:** Cannot create, bind, or modify Roles or RoleBindings.
- **No Container Execution:** `pods/exec`, `pods/attach`, and `pods/portforward` are omitted.
- **No Cluster-Scoped Access:** Zero ClusterRoles or ClusterRoleBindings. Cannot view or access other namespaces (e.g. `kube-system`) or host nodes.
- **Helm Driver Demarcation:** In Phase D8.4/D8.5, Helm will operate with `HELM_DRIVER=configmap`, utilizing the authorized `configmaps` verbs without requiring `secrets` access.

## 5. Phase D: Remediated Admission Controls (Two-Policy Architecture)

Located in `k8s/rbac/jenkins-admission-policy.yaml`:

### 5.1 CEL Type-Safety Architecture: Two Independent Policies
The initial design unified Deployments, Jobs, and Services under one ValidatingAdmissionPolicy using runtime short-circuit prefixes (`request.resource.resource == 'services' || (...)`). However, Kubernetes CEL evaluates expressions against the OpenAPI schemas of all matched resources at policy creation time. Because `object.spec.template` does not exist on `core/v1 ServiceSpec`, and `object.spec.type` / `externalIPs` / `ports` / `loadBalancer` do not exist directly on `apps/v1 DeploymentSpec` or `batch/v1 JobSpec`, unified schema matching causes CEL static type-checking errors during admission registration.

To guarantee complete CEL static type safety, the admission control layer is partitioned into two independent `ValidatingAdmissionPolicy` and `ValidatingAdmissionPolicyBinding` pairs:

1. **Workload Policy (`docvault-deployer-workload-guardrails`):**
   - Matches exclusively `apps/v1 Deployments` and `batch/v1 Jobs`.
   - Contains Rules 1–13. All expressions operate directly on `object.spec.template.spec` without obsolete runtime short-circuit prefixes.
   - Enforces exact Alembic migration command allowlisting exclusively on `jobs`.
2. **Service Policy (`docvault-deployer-service-guardrails`):**
   - Matches exclusively core `v1 Services`.
   - Contains Rules 1–5 (formerly 14–18). All expressions operate directly on `object.spec` without obsolete runtime short-circuit prefixes.
   - Restricts Services strictly to internal `ClusterIP` and prohibits external exposure.

Both policies enforce `failurePolicy: Fail` and strictly scope enforcement to requests authenticated as `system:serviceaccount:docvault:jenkins-deployer` via CEL match conditions on `request.userInfo.username`. Administrator deployments bypass these policies.

### 5.2 Complete Register of Split CEL Guardrails

#### Policy 1: `docvault-deployer-workload-guardrails`
```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: docvault-deployer-workload-guardrails
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - apiGroups: ["apps"]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["deployments"]
      - apiGroups: ["batch"]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["jobs"]
  matchConditions:
    - name: is-jenkins-deployer
      expression: "request.userInfo.username == 'system:serviceaccount:docvault:jenkins-deployer'"
  validations:
    # 1. Prohibit host namespaces (hostNetwork, hostPID, hostIPC)
    - expression: "(!has(object.spec.template.spec.hostNetwork) || !object.spec.template.spec.hostNetwork) && (!has(object.spec.template.spec.hostPID) || !object.spec.template.spec.hostPID) && (!has(object.spec.template.spec.hostIPC) || !object.spec.template.spec.hostIPC)"
      message: "Host namespaces (hostNetwork, hostPID, hostIPC) are prohibited."

    # 2. Prohibit privileged mode and require allowPrivilegeEscalation: false
    - expression: "object.spec.template.spec.containers.all(c, (!has(c.securityContext) || !has(c.securityContext.privileged) || !c.securityContext.privileged) && (has(c.securityContext) && has(c.securityContext.allowPrivilegeEscalation) && !c.securityContext.allowPrivilegeEscalation)) && (!has(object.spec.template.spec.initContainers) || object.spec.template.spec.initContainers.all(c, (!has(c.securityContext) || !has(c.securityContext.privileged) || !c.securityContext.privileged) && (has(c.securityContext) && has(c.securityContext.allowPrivilegeEscalation) && !c.securityContext.allowPrivilegeEscalation)))"
      message: "Privileged mode is prohibited and allowPrivilegeEscalation must be false across all containers and initContainers."

    # 3. Require runAsNonRoot: true at Pod level and prohibit container-level override to false
    - expression: "has(object.spec.template.spec.securityContext) && has(object.spec.template.spec.securityContext.runAsNonRoot) && object.spec.template.spec.securityContext.runAsNonRoot && object.spec.template.spec.containers.all(c, !has(c.securityContext) || !has(c.securityContext.runAsNonRoot) || c.securityContext.runAsNonRoot) && (!has(object.spec.template.spec.initContainers) || object.spec.template.spec.initContainers.all(c, !has(c.securityContext) || !has(c.securityContext.runAsNonRoot) || c.securityContext.runAsNonRoot))"
      message: "Pod spec must enforce runAsNonRoot: true and no container or initContainer may override runAsNonRoot to false."

    # 4. Mandatory Linux capabilities: drop ALL, no added capabilities
    - expression: "object.spec.template.spec.containers.all(c, has(c.securityContext) && has(c.securityContext.capabilities) && has(c.securityContext.capabilities.drop) && c.securityContext.capabilities.drop.exists(d, d == 'ALL') && (!has(c.securityContext.capabilities.add) || c.securityContext.capabilities.add.size() == 0)) && (!has(object.spec.template.spec.initContainers) || object.spec.template.spec.initContainers.all(c, has(c.securityContext) && has(c.securityContext.capabilities) && has(c.securityContext.capabilities.drop) && c.securityContext.capabilities.drop.exists(d, d == 'ALL') && (!has(c.securityContext.capabilities.add) || c.securityContext.capabilities.add.size() == 0)))"
      message: "Containers and initContainers must drop ALL capabilities and cannot add capabilities."

    # 5. Prohibit hostPath volumes
    - expression: "!has(object.spec.template.spec.volumes) || object.spec.template.spec.volumes.all(v, !has(v.hostPath))"
      message: "hostPath volumes are prohibited."

    # 6. Prohibit direct or projected Secret volume mounts
    - expression: "!has(object.spec.template.spec.volumes) || object.spec.template.spec.volumes.all(v, !has(v.secret) && (!has(v.projected) || !has(v.projected.sources) || v.projected.sources.all(s, !has(s.secret))))"
      message: "Direct or projected Secret volume mounts are prohibited."

    # 7. Prohibit Secret-backed environment variables (secretKeyRef or envFrom secretRef)
    - expression: "object.spec.template.spec.containers.all(c, (!has(c.env) || c.env.all(e, !has(e.valueFrom) || !has(e.valueFrom.secretKeyRef))) && (!has(c.envFrom) || c.envFrom.all(ef, !has(ef.secretRef)))) && (!has(object.spec.template.spec.initContainers) || object.spec.template.spec.initContainers.all(c, (!has(c.env) || c.env.all(e, !has(e.valueFrom) || !has(e.valueFrom.secretKeyRef))) && (!has(c.envFrom) || c.envFrom.all(ef, !has(ef.secretRef)))))"
      message: "Secret-backed environment variables (valueFrom.secretKeyRef or envFrom.secretRef) are prohibited."

    # 8. Prohibit host ports
    - expression: "object.spec.template.spec.containers.all(c, !has(c.ports) || c.ports.all(p, !has(p.hostPort) || p.hostPort == 0)) && (!has(object.spec.template.spec.initContainers) || object.spec.template.spec.initContainers.all(c, !has(c.ports) || c.ports.all(p, !has(p.hostPort) || p.hostPort == 0)))"
      message: "Host ports are prohibited."

    # 9. Enforce ServiceAccount docvault-app, explicit automountServiceAccountToken: false, and zero projected tokens
    - expression: "has(object.spec.template.spec.automountServiceAccountToken) && !object.spec.template.spec.automountServiceAccountToken && has(object.spec.template.spec.serviceAccountName) && object.spec.template.spec.serviceAccountName == 'docvault-app' && (!has(object.spec.template.spec.volumes) || object.spec.template.spec.volumes.all(v, !has(v.projected) || !has(v.projected.sources) || v.projected.sources.all(s, !has(s.serviceAccountToken))))"
      message: "Workload must explicitly specify automountServiceAccountToken: false, serviceAccountName: docvault-app, and zero projected serviceAccountToken volumes."

    # 10. Prohibit initContainers entirely for deployment identity
    - expression: "!has(object.spec.template.spec.initContainers) || object.spec.template.spec.initContainers.size() == 0"
      message: "initContainers are prohibited for deployment identity."

    # 11. Restrict image repository to iyedbnaissa/docvault-api with immutable sha256 digest
    - expression: "object.spec.template.spec.containers.all(c, c.image.matches('^iyedbnaissa/docvault-api@sha256:[a-f0-9]{64}$')) && (!has(object.spec.template.spec.initContainers) || object.spec.template.spec.initContainers.all(c, c.image.matches('^iyedbnaissa/docvault-api@sha256:[a-f0-9]{64}$')))"
      message: "Container image must be from iyedbnaissa/docvault-api with an immutable sha256 digest."

    # 12. Prohibit arbitrary command and args overrides (allowlisting exact Alembic migration command on Jobs only)
    - expression: "object.spec.template.spec.containers.all(c, (request.resource.resource != 'jobs' && (!has(c.command) || c.command.size() == 0) && (!has(c.args) || c.args.size() == 0)) || (request.resource.resource == 'jobs' && (((!has(c.command) || c.command.size() == 0) && (!has(c.args) || c.args.size() == 0)) || (has(c.command) && c.command == ['alembic', '-c', 'alembic.ini', 'upgrade', 'head'] && (!has(c.args) || c.args.size() == 0))))) && (!has(object.spec.template.spec.initContainers) || object.spec.template.spec.initContainers.all(c, (!has(c.command) || c.command.size() == 0) && (!has(c.args) || c.args.size() == 0)))"
      message: "Container command and args overrides are prohibited (only exact allowlisted Alembic migration command is permitted on Jobs)."

    # 13. Prohibit imagePullSecrets on deployment templates
    - expression: "!has(object.spec.template.spec.imagePullSecrets) || object.spec.template.spec.imagePullSecrets.size() == 0"
      message: "imagePullSecrets are prohibited on deployment templates."
```

## 5.4 Private Docker Hub Authentication Architecture (Task 1 Evaluation)

### 5.4.1 Authentication Mechanisms Evaluated
1. **Mechanism A — Node-Level containerd Registry Authentication (`/etc/rancher/k3s/registries.yaml`):**
   - K3s embeds containerd and natively supports `/etc/rancher/k3s/registries.yaml` (file mode `0600`, owned by `root:root`).
   - Containerd authenticates directly with `docker.io` upon pulling `iyedbnaissa/docvault-api` images.
   - **Security Properties:** Zero Kubernetes Secrets are stored in etcd or mounted in namespaces; zero Pod template modifications are required; credentials remain strictly on the host under root isolation.
2. **Mechanism B — ServiceAccount-Level `imagePullSecrets` on `docvault-app`:**
   - Administrator creates a `kubernetes.io/dockerconfigjson` Secret in namespace `docvault` out-of-band and links it to `ServiceAccount/docvault-app`:
     ```bash
     kubectl create secret docker-registry docvault-registry-creds \
       --namespace=docvault \
       --docker-server=https://index.io.docker/v1/ \
       --docker-username=<USER> \
       --docker-password=<TOKEN>
     kubectl patch serviceaccount docvault-app -n docvault -p '{"imagePullSecrets": [{"name": "docvault-registry-creds"}]}'
     ```
   - **Admission Controller Injection Behavior:** The built-in Kubernetes `ServiceAccount` admission controller inspects newly created `core/v1 Pod` objects at Pod admission time and automatically appends the ServiceAccount's `imagePullSecrets` to the `pod.spec.imagePullSecrets` field.
   - **Crucial Architecture Finding:** The built-in admission controller mutates `core/v1 Pod` objects; it **NEVER** mutates `apps/v1 Deployment` or `batch/v1 Job` templates upon submission.

### 5.4.2 Compatibility with ValidatingAdmissionPolicy (Rule 13)
- `ValidatingAdmissionPolicy` rule 13 enforces:
  `request.resource.resource == 'services' || (!has(object.spec.template.spec.imagePullSecrets) || object.spec.template.spec.imagePullSecrets.size() == 0)`
- `jenkins-deployer` submits `apps/v1 Deployment` and `batch/v1 Job` objects whose Pod templates omit `imagePullSecrets`. These objects comply with Rule 13 and pass admission without violation.
- When the Deployment or Job controller creates live Pods, those requests are generated by `system:serviceaccount:kube-system:replicaset-controller` or `system:serviceaccount:kube-system:job-controller`, not `jenkins-deployer`. The actor match condition (`request.userInfo.username == 'system:serviceaccount:docvault:jenkins-deployer'`) skips controller-created Pods.
- **Conclusion:** Both mechanisms are technically viable and secure. Mechanism A (node-level containerd) provides the cleanest privilege boundary by avoiding registry Secrets in etcd altogether, while Mechanism B is fully compatible with Rule 13 because the built-in admission controller injects pull secrets only at the Pod level, leaving Deployments and Jobs untainted.

## 5.5 Database Migration Job Compatibility Architecture (Task 2 Evaluation)

### 5.5.1 Container ENTRYPOINT and Migration Commands
- Inspection of `backend/Dockerfile` reveals:
  - No `ENTRYPOINT` is defined.
  - `CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]` is the default.
  - Running a container from `iyedbnaissa/docvault-api` without overriding `command` launches the FastAPI web server, not Alembic migrations.
- In `compose.yaml`, database migrations execute:
  `command: ["alembic", "-c", "alembic.ini", "upgrade", "head"]`.

### 5.5.2 Narrowest Secure Remediation for Rule 12
- Prohibiting all `command` and `args` overrides prevented legitimate database migration Jobs.
- Allowing arbitrary commands would violate least privilege and create an arbitrary code execution vector.
- **Narrowest Secure Design:**
  - On `batch/v1 jobs`, CEL evaluates whether `command` is either empty OR strictly equal to `['alembic', '-c', 'alembic.ini', 'upgrade', 'head']`, while strictly requiring `args` to be empty or omitted.
  - On `apps/v1 deployments`, all `command` and `args` overrides remain strictly prohibited.
  - This guarantees that Jenkins cannot launch arbitrary binaries or pass malicious flags, while enabling headless schema migration execution.

### 5.5.3 Least-Privilege Database Credential Separation
- In DocVault's architecture, database roles are strictly partitioned:
  - `docvault_app`: DML privileges only (`SELECT`, `INSERT`, `UPDATE`, `DELETE`).
  - `docvault_migrator`: DDL privileges (`CREATE`, `ALTER`, `DROP`, `REFERENCES`).
- `ValidatingAdmissionPolicy` Rule 6 (no direct or projected Secret volumes) and Rule 7 (no Secret-backed environment variables) prevent `jenkins-deployer` from mounting credentials or reading database passwords from Secrets.
- **Operational Requirement:**
  - Automated deployment by `jenkins-deployer` cannot directly mount migrator credentials.
  - Database schema migrations should either be executed out-of-band by an authorized administrator prior to deployment, or orchestrated via an isolated administrator-managed migration pipeline that does not grant Jenkins access to migrator credentials.
