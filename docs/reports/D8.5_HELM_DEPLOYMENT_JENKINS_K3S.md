## 1. Executive Summary & Critical Feasibility Assessment

Phase D8.5 designs, validates, and scaffolds the Helm deployment path for DocVault:
**GitHub Actions CI Gates → Jenkins CD Controller → Helm v3 → K3s Admission Controls → DocVault Application**.

### Critical Feasibility Assessment (Section 4 Stop Condition)
Prior to live application deployment, a forensic feasibility check was executed evaluating the four prerequisites mandated by Section 4:
1. **Database Availability:** **UNSATISFIED (BLOCKER).** There is no PostgreSQL instance running inside K3s. The host's Docker Compose container (`docvault-postgres-1`) is isolated on an internal bridge network (`docvault_database`) with port 5432 unpublished. K3s Flannel pods cannot reach it. The application's `/ready` endpoint performs a live database query (`SELECT 1`), and without database reachability it returns HTTP 503, permanently failing readiness.
2. **Database Credentials Injection:** **UNSATISFIED (BLOCKER).** ValidatingAdmissionPolicy Rules 6 and 7 prohibit `jenkins-deployer` from mounting Secrets as volumes or using Secret-backed environment variables (`secretKeyRef`, `envFrom.secretRef`). Furthermore, Jenkins RBAC excludes `secrets` access, and project rules strictly prohibit plaintext credentials in ConfigMaps, manifests, or Git.
3. **Image-Pull Authorization & Application ServiceAccount:** **UNSATISFIED (BLOCKER).** The container image `iyedbnaissa/docvault-api` is private on Docker Hub. Admission Policy Rule 9 mandates `serviceAccountName: docvault-app`, but `docvault-app` does not exist in namespace `docvault` (and Jenkins cannot create it). Node-level containerd credentials (`/etc/rancher/k3s/registries.yaml`) do not exist, and Rule 13 prohibits `imagePullSecrets` on deployment templates.
4. **Persistent Storage:** **SATISFIED.** K3s provides dynamic volume provisioning via the default `local-path` StorageClass (`rancher.io/local-path`). Jenkins RBAC explicitly permits `create` on `persistentvolumeclaims`, and admission policies allow PVC volume mounts.

> [!CAUTION]
> **Stop Condition Activated:**  
> In strict accordance with Section 4 (*"If database credentials, database availability, image-pull authorization, or persistent storage cannot be provided within the existing security boundaries, stop and report the exact blocker and the smallest administrator action needed. Do not bypass the controls"*), live workload provisioning was halted to prevent spawning broken pods (`ImagePullBackOff` or failed readiness). The complete Helm chart, Jenkinsfile deployment stages, and automated test suite were implemented and verified in server-side admission dry-run mode.

## 2. Minimal Administrator Actions Needed to Unblock Live Rollout

To permit live workload scheduling without violating least privilege or admission policies, the cluster administrator must perform four out-of-band actions:

### Step 1: Provision `ServiceAccount/docvault-app` with Docker Hub Registry Secret
Create the required `docvault-app` ServiceAccount with `automountServiceAccountToken: false` and attach the image pull secret out-of-band:
```bash
# 1. Create Docker Hub registry secret
kubectl create secret docker-registry docvault-registry-creds \
  --namespace=docvault \
  --docker-server=https://index.docker.io/v1/ \
  --docker-username=<dockerhub-username> \
  --docker-password=<dockerhub-token>

# 2. Provision approved ServiceAccount with linked imagePullSecret
kubectl apply -f - <<EOF
apiVersion: v1
kind: ServiceAccount
metadata:
  name: docvault-app
  namespace: docvault
automountServiceAccountToken: false
imagePullSecrets:
  - name: docvault-registry-creds
EOF
```
*Result:* Satisfies Rule 9 (`serviceAccountName: docvault-app`, `automountServiceAccountToken: false`) and Rule 13 (Deployment template omits `imagePullSecrets`; Kubernetes ServiceAccount admission controller automatically injects the pull secret at Pod creation).

### Step 2: Establish PostgreSQL Database Reachability in K3s
Deploy a standard PostgreSQL 17 instance in namespace `docvault` exposing a ClusterIP Service named `docvault-postgres` on port 5432, with the `docvault` database created.

### Step 3: Authorize Database Credential Injection Pattern
Because Rule 7 prohibits `valueFrom.secretKeyRef` generically for `jenkins-deployer`, update `docvault-deployer-workload-guardrails` with a narrow, approved exception for the application database secret:
```cel
# Allow reference only to the administrator-managed secret 'docvault-app-db-creds'
object.spec.template.spec.containers.all(c,
  (!has(c.env) || c.env.all(e, !has(e.valueFrom) || !has(e.valueFrom.secretKeyRef) || e.valueFrom.secretKeyRef.name == 'docvault-app-db-creds')) &&
  (!has(c.envFrom) || c.envFrom.all(ef, !has(ef.secretRef)))
)
```
Then create `docvault-app-db-creds` containing `DATABASE_PASSWORD`.

### Step 4: Execute Initial Database Migrations
Run the initial Alembic schema migration (`alembic -c alembic.ini upgrade head`) using migrator credentials (`docvault_migrator`) out-of-band or via an authorized migration Job.
